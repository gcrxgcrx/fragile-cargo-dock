# Repair test: is the best LLM candidate's failure a *scale* problem or a *reachability* problem?

Written before any of the six trainings was launched. Base candidate:
`runs/env_007/prompt_ladder/L2/cand_00/reward_v1.py` — the strongest structurally-compliant
LLM candidate (event ✔, second ✔, `docked_raw` +30, gentleness gap 1.14, terminal ratio ∞)
and **0/60** on fresh seeds.

## Why this experiment

`runs/env_007/LADDER_FINDINGS.md` §2 measured the failure mechanism: the candidate's own
decisive terms are never active on the trajectory its policy produces
(`crate_to_dock_progress` active_rate **0.0089**, +0.0047 per episode;
`dock_speed_penalty` active_rate 0.0039, −0.078 per episode; `success_event` **0.0**), so the
realised reward is ≈0 and there is no gradient to climb. Two rival explanations remain:

* **(a) scale** — the terms are right but too small relative to everything else;
* **(b) reachability** — the terms are gated on states the policy never visits.

Note an arithmetic constraint that already limits (a): the harness clips the per-step reward
to 20, so the candidate's +300 one-off event is delivered as **+20** — exactly what a dense
+20/step term earns in a single step. Raising the *event's* magnitude therefore cannot change
the per-step landscape at all. A scale test must be run on the **dense** term.

## Arms (all generated by `make_repair_variants.py`, edits recorded in each file header)

| arm | edit relative to `L2/cand_00` | tests |
|---|---|---|
| `r00_copy` | none (byte-identical body) | machinery control: must reproduce 0/60 |
| `r01_guidance` | + dense obs-only guidance (probe D's `crate_progress`, `cart_approach`, weight 1) | reachability |
| `r02_guidance_gentle` | `r01` + probe D's obs-only gentleness (−0.05·contact·closing) | reachability + the term probe D shows is decisive |
| `r03_guidance_x3` | `r01` with the guidance backbone at weight 3 | is more guidance better? |
| `r04_own_progress_x50` | its **own** `crate_to_dock_progress` coefficient 12 → 600, nothing added | the scale hypothesis on the dense term |
| `r05_guidance_no_events` | `r02` with the candidate's own `enter_dock_event`/`success_event` zeroed | is its payoff term functional once reachable? |

The guidance formulas are copied from `ablation_probe/probeD_obs_gentleness.py` and are
observation-only (no `info`), so every arm stays inside the declared contract.

## Protocol (fixed)

`configs/env007_terminal_rule_pilot.yaml`, `n_envs=6`, clip **20**, **1.2M** steps, seed 0 —
identical to every other run in this project. Scored on fresh seeds **32000–32059**
(60 episodes), via `eval_pool.py`, so seeds 30000–30059 stay pristine. Launched through
`runs/env_007/train_queue.ps1` (`-MaxParallel 4`, commit-guarded).

## Predictions, fixed before launching

| # | prediction | rationale |
|---|---|---|
| **P1** | `r00_copy` = **0/60** | byte-identical copy; if this fails the machinery is broken and no other comparison counts |
| **P2** | `r01_guidance` **≥ 12/60 (20 %)** | a dense backbone is active from step 0, so a path to the dock exists for the candidate's own +300 event to pay |
| **P3** | `r02 ≥ r01` | probe D (control v1 + gentleness) is the best obs-only arm at 73.3 %, so gentleness should not hurt |
| **P4** | `r04 < 12/60` and `r04 ≤ r01` | scaling its own progress coefficient ×50 changes magnitude but not reachability: the term stays gated on approaching the dock (active 0.9 % of steps) |
| **P5** | `r05 < r02` | the candidate's own terminal events are a *real payoff* once the policy can reach them; removing them should hurt |
| **P6** | in `r01`/`r02`, `success_event` **active_rate > 0**; in `r04` it stays ≈0 | mechanism check read straight from `training_summary.json`, independent of the outcome |

## Interpretation rules, fixed now

* If **P2 holds** → the LLM failure is a *reachability* gap closable by adding a known dense
  backbone. The concrete target for a repair operator is then "add an unconditionally active
  guidance term", and P5 tells us whether the candidate's own payoff survives.
* If **P1 holds and P2 fails** → the gap is **not** closable by this localized structural
  addition, which weakens the case for building a repair loop (H2 in `NEXT_SESSION.md`).
* If **P4 holds** while P2 holds → the two hypotheses are separated in the cleanest possible
  way: magnitude alone does not rescue the candidate, structure does.
* If **P1 fails** → treat the whole run as void and fix the generator before interpreting
  anything.

## Standing caveat

This is a **human-oracle upper bound** in the sense of `SESSION_STATE.md` §4 error #7. It
measures whether a repairable target *exists* and how large the fix has to be; it is **not**
evidence that a search would find the edit, and it must never be reported as a method result.

## ADDENDUM (written 19:52, after the mechanism readouts of `r00`–`r03`, before `r04`–`r07` finished)

**What was observed, and what it changed.** The component tables of the first four arms
(`component_shares.md`) show that **the guidance backbone did not do what the original
prediction assumed**: `success_event` `active_rate` is still exactly **0.0** in `r01`, `r02`
and `r03`, the whole realised reward is ~1e−3 per episode, and the dominant component is
`REPAIR_cart_approach` at 88–100 % **of a near-zero total**. So P6 is already falsified and
P2 is in doubt: adding the same dense terms a working hand-written arm has does not connect
this candidate to its payoff.

That prompted a sharper reading of why the hand-written arms work. Re-checking
`component_share_report.py` output for the working arms: the term that dominates them is not
progress shaping at all but a **dense payoff at the goal** — probe D's `dock_settled_hold`
at 96 % of the mass, +140…+180 per episode. `L2/cand_00` has only a **one-off** +300 event,
and under the harness's per-step clip of 20 a one-off event can never be worth more than
**one** step of such a stream (a +300 event is delivered as +20; a +20/step stream pays
+20 every step).

**Two arms were therefore added** (`make_repair_variants.py`, generated and validated the
same way):

| arm | edit | hypothesis |
|---|---|---|
| `r06_settled_stream` | base + `20.0 * done_cond` per step — the candidate's own success predicate, paid densely, exactly as `probeD`'s `dock_settled_hold` is | the missing ingredient is a dense goal payoff |
| `r07_stream_and_guidance` | `r02` + the same dense stream | both together |

**Prediction, fixed before these two runs finish:** `r06 > 0/60` and `r06 > r01` — i.e. the
one-off→stream conversion is the operative repair, and dense *guidance* is neither necessary
nor sufficient on its own. If `r06` is still 0/60, then none of {guidance, gentleness,
dense payoff} added individually or together rescues the candidate, and the repair-loop
hypothesis (H2) loses its concrete target.

**Disclosure of ordering**, so the reader can judge it: this addendum was written after
reading the *in-training* component tables and the `termination_breakdown`
(`terminated=0, truncated=20`) of `r00`–`r03`, and **before** any fresh-seed outcome for the
repair arms was measured and before `r04`–`r07` were run. P1–P5 stand as originally fixed;
P6 (mechanism) is already falsified for `r01`/`r02`; the `r06`/`r07` prediction above is
recorded before their results exist.

## ADDENDUM 2 — wave 3, built on the `r04` measurement (written 19:57)

**What wave 1 measured** (fresh seeds 32000–32059, 60 episodes; full table in
`runs/env_007/REPAIR_TEST_FINDINGS.md`):

* `r00_copy` = **0/60, dock 0.00, mean final goal distance 4.148** — byte-identical to the
  base candidate, so the machinery is validated (P1 ✔);
* `r01`/`r02`/`r03` (guidance, guidance+gentleness, guidance×3) = **0/60, dock 0.00,
  goal distance 4.148–4.089** — the guidance backbone did **not** make the cart move the
  crate at all, so **P2 and P6 are falsified**;
* **`r04_own_progress_x50`** — *nothing added*, only the candidate's own progress
  coefficient 12 → 600 — = **0/60 but `dock_entered` 0.97 and mean final goal distance
  0.140**. All 60 episodes end on `time_limit`; no hard impacts, no out-of-bounds.

So the failure decomposes into two layers, and a single constant fixes the first:
**(i) reaching the dock region** (a ×50 change on the candidate's own progress term gets the
crate from 4.148 m to 0.14 m and into the dock in 97 % of episodes) and
**(ii) satisfying the success predicate** — inside AND aligned AND `speed < 0.05 m/s` for
**10 consecutive steps**. The reward pays for *approaching*, so the policy keeps pushing and
never settles. Its own `dock_speed_penalty` (−3·near_dock·max(0, speed−0.05)) is far too
weak to stop that, consistent with `SESSION_STATE.md` §5's note that the settling weight
needs to be 30–100× the natural value.

**Wave 3 arms** — each adds exactly one settling lever to `r04`'s essential change:

| arm | edit relative to `r04` |
|---|---|
| `r08_progress_x50_gentle` | + probe D's obs-only gentleness (a settling **penalty**) |
| `r09_progress_x50_stream` | + the dense settled **payoff** stream (`+20·done_cond` per step) |
| `r10_x50_stream_gentle` | + both levers |
| `r11_x50_own_speedpen_x100` | + the candidate's **own** `dock_speed_penalty` coefficient −3 → −300 |

**Predictions, fixed before launching:**

| # | prediction |
|---|---|
| **S1** | at least one of `r08`/`r09`/`r10` reaches **> 0/60** — the missing ingredient is a settling incentive, not reachability |
| **S2** | `r09 ≥ r08` — a dense payoff for *being* settled is a stronger settling incentive than a penalty for moving |
| **S3** | `r10 ≥ max(r08, r09)` — both levers together are at least as good as either |
| **S4** | `r11 > 0/60` would show the candidate's own terms can be rebalanced by scale alone, with no new term at all; a null result for `r11` while S1 holds localises the fix to *adding a payoff*, not *raising a penalty* |
| **S5** | mechanism: in whichever arm succeeds, `success_event` `active_rate` becomes **> 0** — the one-off payoff was always there and only needed to be reached |

**Interpretation fixed now.** If S1 holds, the LLM candidate is repairable, but the repair is
**two coordinated edits** (a ×50 coefficient on one term *and* a new settling payoff term),
not one — which is the concrete answer to whether this gap counts as a *small localized edit*
for the purposes of `HANDOFF_QUESTIONS.md` P1–P5. If S1 fails with all four levers, then no
combination of {scale, guidance, gentleness, dense payoff} tried here rescues the candidate,
and H2 loses its concrete target on this arm.
