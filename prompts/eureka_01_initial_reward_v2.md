你是奖励函数设计专家。请根据给定的环境事实与接口约束，写出**一个完整可执行的奖励函数**。

# 环境事实

你只能依据下面给出的事实理解任务、观测与动作。不要猜测环境名称，不要发明未声明的变量或维度。

# 你可以使用的输入

奖励函数签名必须逐字符一致：

```python
def compute_reward(obs, action, next_obs, original_reward, info, training_progress=0.0):
```

- `obs`：动作前的观测（单步向量，不累积历史）
- `action`：在该观测上执行的动作
- `next_obs`：动作后的观测
- `original_reward`：**禁止使用**
- `info`：元数据字典，本环境未开放任何可读字段
- `training_progress`：可选的训练进度标量，`[0, 1]`，默认不使用

# 设计方法

1. 先确定任务的主行为语义（例如：任务进展、状态稳定、目标事件、动作代价）。
2. 把每个语义实现为一个**具名组件**，各自独立记录在 `components` 字典中。
3. 总奖励是各组件之和，权重决定其量级。
4. 组件要和任务成败同向：能让策略真正完成任务，而不是只优化代理指标。
5. 注意量级平衡：单个惩罚项每步的绝对值不应压过主信号；过多的惩罚会让策略不敢动。

# 必须避免的激励冲突（违反即无效）

任何辅助组件（低速、稳定、对齐、平滑等）都**不允许因为"推进任务所必需的动作"而下降**。

典型反例：用 `k / (1 + c * speed)` 形式的"低速因子"作为**持续的全局状态奖励**。推动目标物体必然产生速度，于是该组件在惩罚任务进展本身；一旦它的量级压过主信号，最优策略就变成"什么都不做"。

要求：
- "低速 / 静止 / 对齐"这类量只能作为**门控**——乘在任务进展信号上，或仅在**已经接近目标**时激活；**不得作为全局持续奖励**被动收分。
- 任何组件都不得对"把目标推向目标位置"这一行为产生净负贡献。

**必做自检 ①**：把奖励分别代入 ①智能体什么都不做、目标静止在**初始位置**；②智能体正在把目标**推向目标位置**（目标因此具有速度）。要求 **②的单步总奖励严格高于 ①**。做不到就重新设计。

# 必须让"完成事件"主导过程信号（违反即无效）

任务成功是一个**一次性事件**，不是一段可以长期停留的状态：货箱必须进入泊位容差区、速度降到阈值以下、
并连续保持若干步，且**一旦满足，episode 立即结束**。

如果奖励里只有过程型信号（接近度、推进量、稳定度），而没有任何一个"完成"事件的大额奖励，那么
"一直在路上推""停在泊位附近慢慢磨"这类**能持续收分但永远不完成**的行为就会成为局部最优：
过程信号可以在 400 步里一直收，而"完成"只发生一次。

量级判据（必须满足，否则奖励无效）：

- 设 `B` = 满足完成条件时的**单步奖励**。由于完成后最多再累积"保持步数"次就被截断，
  `B` 必须满足 `10 * B > 3 * (所有过程型组件的单步奖励上限之和 * 400)`。
  即：**完成一次的总回报，必须严格压过"400 步都在接近但从未完成"的总回报**（约 3 倍余量）。

其他要求：

- 完成条件必须从 `obs` **显式推断**，且容差**只能**取自上面环境事实里给出的泊位几何与阈值，
  不得自创更宽松的判据。反例：用 `dist < 1.5` 当作"到位"——环境事实里已经写明
  "货箱中心离泊位中心 0.30 m 不算交付"，用 1.5 当阈值会让策略停在 1.5 m 外一直收分。
- 过程型组件**不得在未完成区域收满**：接近类信号应是**增量**形式（只在"这一帧更接近了"时给分），
  而不是纯接近度（停在附近就能一直收分）。

**必做自检 ②**：把奖励分别代入
③"货箱停在泊位外 0.3 m 处、速度接近 0、保持 400 步"（悬停收割）；
④"货箱真正进入泊位容差区并停稳，连续保持到 episode 结束"。
要求 **④整条轨迹的累计回报严格高于 ③**。做不到就加大完成奖励、或把过程信号改成增量形式；
**不允许**通过放宽完成判据来让 ④ 变容易。
