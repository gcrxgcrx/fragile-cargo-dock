你是奖励函数设计专家。请根据给定的环境事实与接口约束，写出**一个完整可执行的奖励函数**。

# 环境事实

你只能依据下面给出的事实理解任务、观测与动作。不要猜测环境名称，不要发明未声明的变量或维度。

# 你可以使用的输入

奖励函数签名必须逐字符一致：

```python
def compute_reward(obs, action, next_obs, original_reward, info, training_progress=0.0):
```

- `obs`：动作前的观测（单步向量，不累积历史）
- `action`：在该观测上执行的动作
- `next_obs`：动作后的观测
- `original_reward`：**禁止使用**
- `info`：元数据字典，本环境未开放任何可读字段
- `training_progress`：可选的训练进度标量，`[0, 1]`，默认不使用

# 设计方法

1. 先确定任务的主行为语义（例如：任务进展、状态稳定、目标事件、动作代价）。
2. 把每个语义实现为一个**具名组件**，各自独立记录在 `components` 字典中。
3. 总奖励是各组件之和，权重决定其量级。
4. 组件要和任务成败同向：能让策略真正完成任务，而不是只优化代理指标。
5. 注意量级平衡：单个惩罚项每步的绝对值不应压过主信号；过多的惩罚会让策略不敢动。

# 必须避免的激励冲突（违反即无效）

任何辅助组件（低速、稳定、对齐、平滑等）都**不允许因为"推进任务所必需的动作"而下降**。

典型反例：用 `k / (1 + c * speed)` 形式的"低速因子"作为**持续的全局状态奖励**。推动目标物体必然产生速度，于是该组件在惩罚任务进展本身；一旦它的量级压过主信号，最优策略就变成"什么都不做"。

要求：
- "低速 / 静止 / 对齐"这类量只能作为**门控**——乘在任务进展信号上，或仅在**已经接近目标**时激活；**不得作为全局持续奖励**被动收分。
- 任何组件都不得对"把目标推向目标位置"这一行为产生净负贡献。

**必做自检 ①**：把奖励分别代入 ①智能体什么都不做、目标静止在**初始位置**；②智能体正在把目标**推向目标位置**（目标因此具有速度）。要求 **②的单步总奖励严格高于 ①**。做不到就重新设计。

# 必须让"完成事件"主导过程信号（违反即无效）

任务成功是一个**一次性事件**，不是一段可以长期停留的状态：货箱必须进入泊位容差区、速度降到阈值以下、
并连续保持若干步，且**一旦满足，episode 立即结束**。

如果奖励里只有过程型信号（接近度、推进量、稳定度），而没有任何一个"完成"事件的大额奖励，那么
"一直在路上推""停在泊位附近慢慢磨"这类**能持续收分但永远不完成**的行为就会成为局部最优：
过程信号可以在 400 步里一直收，而"完成"只发生一次。

量级判据（必须满足，否则奖励无效）：

- 设 `B` = 满足完成条件时的奖励。由于完成后最多再累积"保持步数"次就被截断，
  `B` 必须满足 `10 * B > 3 * (所有过程型组件的单步奖励上限之和 * 400)`。
  即：**完成一次的总回报，必须严格压过"400 步都在接近但从未完成"的总回报**（约 3 倍余量）。

其他要求：

- 完成条件必须从 `obs` **显式推断**，且容差**只能**取自上面环境事实里给出的泊位几何与阈值，
  不得自创更宽松的判据。反例：用 `dist < 1.5` 当作"到位"——环境事实里已经写明
  "货箱中心离泊位中心 0.30 m 不算交付"，用 1.5 当阈值会让策略停在 1.5 m 外一直收分。
- 过程型组件**不得在未完成区域收满**：接近类信号应是**增量**形式（只在"这一帧更接近了"时给分），
  而不是纯接近度（停在附近就能一直收分）。

**必做自检 ②**：把奖励分别代入
③"货箱停在泊位外 0.3 m 处、速度接近 0、保持 400 步"（悬停收割）；
④"货箱真正进入泊位容差区并停稳，连续保持到 episode 结束"。
要求 **④整条轨迹的累计回报严格高于 ③**。做不到就加大完成奖励、或把过程信号改成增量形式；
**不允许**通过放宽完成判据来让 ④ 变容易。

# 必须包含"接触轻柔度"信号（违反即无效）

任务要求货箱被**轻柔**搬运：撞击过重会损坏货箱并直接判失败。这是本环境成败的**核心技能**，
因为小车没有刹车——它必须"接近目标时提前松手，让地面阻力把货箱带进去"，而不是一直推到最后一刻。

请注意：**观测里没有冲量 / 撞击力这一维**。只有：
接触标志 `obs[14]`、小车前向速度 `obs[4]` 与朝向 `obs[2]`, `obs[3]`、货箱世界速度 `obs[8]`, `obs[9]`。

因此你必须**自己构造**一个可观测的"接近速度"代理，并在接触时惩罚它：

```python
crate_vx = next_obs[8] * 3.0
crate_vy = next_obs[9] * 3.0
crate_along_heading = crate_vx * obs[2] + crate_vy * obs[3]   # 货箱速度沿车头方向的分量
closing = obs[4] * 3.0 - crate_along_heading                  # 正在接近的速度
if closing < 0.0:
    closing = 0.0
contact = 1.0 if next_obs[14] > 0.5 else 0.0
gentleness = -0.05 * contact * closing                        # 建议 k ≈ 0.05
```

要求：

- 该项在**接触中且在接近**（`closing > 0`）时必须为负，权重与主推进信号同量级（建议 `k ≈ 0.05`）。
- 该项**不得**在"接触但未接近"（`closing ≈ 0`）时产生惩罚——**正常匀速推箱不能被判为撞击**，
  否则策略会因为害怕惩罚而不敢推（这是比不做更糟的失败）。
- 这是本环境**唯一**能教会策略"接近泊位时减速"的信号。没有它，策略会把货箱推进泊位后
  **一直在里面蹭**：实测 43.5 步停留在泊位内，其中仅 4.8 步速度达标，交付率 0%。

**必做自检 ③**：构造两个状态——
⑤"小车与货箱接触、接近速度 1.0 m/s"；
⑥"小车与货箱接触、接近速度 0.05 m/s"。
要求 **⑤的单步总奖励明显低于 ⑥**。

# 完成奖励必须是一次性事件，不能在"成功状态"上每步给分（违反即无效）

环境在"连续 10 步满足完成条件"时会**立即终止 episode**。由此：

- 如果你在"货箱在泊位内 + 对齐 + 慢"这个**状态**上**每步**给分，那么策略的最优解是
  **永远不要走完第 10 步**——只要在第 9 步前后被蹭一下、让连续计数清零，这条收益流就能一直续着。
  实测这种写法让策略在泊位里磨 43 步，30/60 回合达到 5–9 步却从未连续 10 步，交付率 0%。
- 正确写法是**一次性事件**：整个 episode 只发一次。

**允许并推荐使用模块级状态。** 签名里没有 `done`，但 `obs[18]`（已用时间比例）在一个 episode 内
**单调递增**、在重置时**回落**，可以用来检测回合边界：

```python
_PREV_T = [-1.0]
_STREAK = [0]
_PAID = [False]
_ENTERED = [False]

# 进入 compute_reward 后第一件事：
t = float(next_obs[18])
if t < _PREV_T[0] or t <= 1.0 / 400.0:      # 检测到新 episode
    _STREAK[0] = 0
    _PAID[0] = False
    _ENTERED[0] = False
_PREV_T[0] = t

# 完成条件的连续计数（不要用"每步给分"）：
if 满足完成条件:
    _STREAK[0] += 1
else:
    _STREAK[0] = 0

success_event = 0.0
if _STREAK[0] >= 10 and not _PAID[0]:
    _PAID[0] = True
    success_event = 300.0                   # 一次性，整个 episode 只发一次
```

要求：

- 完成奖励必须**一次性**；同一 episode 内不得重复发放。
- 若使用模块级状态，**必须**用 `obs[18]` 检测回合边界并重置，否则状态会跨 episode 污染。
- 可以额外给一次性的"首次进入泊位"奖励（同样整局只发一次），它能帮助策略跨过"进得去但停不住"的坎。

**必做自检 ④**：把 reward 在**同一个"停稳"状态**上连续调用 12 次。
要求累计值**在第一次之后就停止增长**；若线性增长，说明你写成了每步流，必须重写。

# 完成状态下，除一次性事件外其余组件必须恰好为 0（违反即无效）

上一条只要求"一次性事件"，做到还不够。实测中大量候选写出了正确的一次性事件，却仍然失败，
原因是它们在泊位内**顺手**留了一个很小的持久项，例如：

```python
align_bonus = 0.3 * (货箱在容差内且对齐)     # 看起来无害
```

单步 0.3 看似微不足道，但 episode 有 400 步，累积是 **120**；而 +300 的一次性事件会被单步裁剪
压到 **+20**。**120 > 20，持久项照样赢。** 实测这样的候选交付率仍然是 0。

要求：

- 当货箱处于完成状态（在容差内 + 对齐 + 慢）时，**除一次性完成事件之外，其他所有组件的
  单步贡献之和必须恰好为 0**。
- 不允许任何"靠近目标就持续给分"的状态项——对齐奖励、稳定奖励、低速奖励、接近度奖励都一样。
  这类量只能作为**门控**乘在**增量**信号上（例如 `对齐度 × 本帧的靠近增量`），或只作为**惩罚**
  （例如速度过快时扣分），**不得单独作为正项按步累积**。
- 唯一的例外是"首次进入泊位"这类**一次性**事件——它们整局只发一次，不随步数累积，可以保留。

**必做自检 ⑤**：把 reward 在**同一个"停稳"状态**上连续调用 12 次。
要求：**除了发一次性事件的那一次之外，其余 11 次的返回值必须恰好为 0**（|值| < 1e-6）。
只要有任何一次明显非零（哪怕是 0.3），就说明存在持久项，必须删除或改成门控/增量形式。

# 代码约束

- 只用环境事实声明的观测维度与索引，不写 `obs[0:3]` 这类切片。
- 禁止 `terminal_success_reward`、`terminal_failure_penalty`、`original_reward`。
- 禁止 `import`、`class`、`try/except`、`lambda`、`eval/exec/open`。
- **允许模块级变量**（用于自检 ④ 的一次性事件与回合边界检测）；不要使用 `global` 语句，
  用列表或字典等可变容器承载状态。
- **输出顺序必须是：模块级变量声明（如有）→ `def compute_reward(...)` 函数本体。**
  模块级声明必须写在函数**之前**。如果你在函数里使用了 `_STREAK` / `_PREV_T` / `_PAID`
  这类名字，就**必须**在函数之前显式写出它们的初始化，例如：

  ```python
  _PREV_T = [-1.0]
  _STREAK = [0]
  _PAID = [False]

  def compute_reward(obs, action, next_obs, original_reward, info, training_progress=0.0):
      ...
  ```

  **只写用法、不写声明会在运行时直接 NameError，该候选会被判为无效。**
- 平方根写 `** 0.5`；指数写 `2.718281828 ** exponent`。
- 必须给 `components`（或 `reward_components` / `reward_terms`）字典赋值，并返回 `(float(total_reward), components)`。
- 只输出代码（模块级声明 + 函数本体），可以用一个 ```python 代码块包住，不要写解释文字。
